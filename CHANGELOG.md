### Changed

- **api/sso-zelian** — `IS_ZELIAN_ENABLED` devient la **bascule unique** entre « Plane app Zelian » (SSO actif) et « Plane outil externe » (auth Plane native), documentée dans `MODE-INTERNE-OU-EXTERNE.md` à la racine. Le flag ne pilotait jusqu'ici que l'affichage du bouton côté web/space : les routes `/auth/zelian/…` restaient joignables en direct dès lors que les identifiants OAuth traînaient dans l'environnement. `ZelianOAuthProvider.__init__` lit désormais le flag (même motif `get_configuration_value` + défaut env que `instance.py`) et lève `ZELIAN_NOT_CONFIGURED` si la valeur n'est pas la chaîne `"1"` — conformément à la convention des autres flags Plane (`IS_GOOGLE_ENABLED`…), `"true"` ou l'entier `1` n'activent rien. Conséquence : en mode externe, les variables `ZELIAN_*` peuvent rester en place sans rien exposer, et la bascule dans les deux sens ne demande **ni migration, ni rebuild, ni revert git** — seulement `docker restart plane-api-1` (⚠️ `/api/instances/` est caché 2 h). Le code du provider, les 4 routes et les tests restent dans l'arbre quel que soit le mode : c'est un réglage, pas une amputation. Vérifié : **15 tests pytest Docker** (les 12 précédents + 3 neufs : refus avec identifiants présents mais flag à `"0"`, refus si le flag est absent, refus sur valeur truthy non conforme `"true"`) ; le jeu d'env des tests porte désormais `IS_ZELIAN_ENABLED="1"`. Aucun fichier du dépôt de documentation Zelian n'a été touché — le choix interne/externe n'est pas tranché.
- **api/sso-zelian** — Validation E2E locale réussie le 2026-07-13 : flux complet « Sign in with Zelian » → Supabase authorize (PKCE S256) → mire `/oauth/consent` (auto-consent) → callback Plane → `User` + `Account(provider='zelian', provider_account_id=<sub Supabase>)` créés en base. Comportement d'auto-consent documenté : avec `@supabase/auth-js` 2.101.1, un client OAuth first-party est auto-consenti côté serveur — `getAuthorizationDetails()` renvoie `redirect_url` directement, sans phase de consentement manuelle.
