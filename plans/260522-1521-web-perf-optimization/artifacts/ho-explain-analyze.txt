## QUERY 1: HoIssueListView main queryset (workspace-scoped, paginated)

SQL:
  SELECT DISTINCT i.id
  FROM issues i
  WHERE i.workspace_id IN ('<4 workspace UUIDs>')
    AND i.is_draft = FALSE
    AND i.deleted_at IS NULL
    AND i.archived_at IS NULL
    AND i.parent_id IS NULL
  ORDER BY i.id
  LIMIT 100;

EXPLAIN ANALYZE output:
  Limit  (cost=7.15..7.27 rows=24 width=16) (actual time=0.078..0.084 rows=24 loops=1)
    -> Unique  (cost=7.15..7.27 rows=24 width=16) (actual time=0.077..0.081 rows=24 loops=1)
         -> Sort  (cost=7.15..7.21 rows=24 width=16) (actual time=0.076..0.078 rows=24 loops=1)
              Sort Key: id
              Sort Method: quicksort  Memory: 26kB
              -> Seq Scan on issues i  (cost=0.00..6.60 rows=24 width=16)
                                        (actual time=0.013..0.040 rows=24 loops=1)
                   Filter: (NOT is_draft) AND (deleted_at IS NULL) AND (archived_at IS NULL)
                            AND (parent_id IS NULL)
                            AND (workspace_id = ANY('{...}'::uuid[]))
                   Rows Removed by Filter: 19
  Planning Time: 1.001 ms
  Execution Time: 0.136 ms

Analysis:
  - Seq Scan on 43-row table — correct planner decision (index scan has higher overhead at <100 rows)
  - workspace_id index EXISTS but not used — expected for tiny table
  - Execution time: 0.136 ms — negligible DB overhead
  - The observed 407 ms TTFB was NOT caused by DB query time
  - Root cause: multiple concurrent HTTP requests from child view useEffect calls (Track A issue)

## Decision: No backend query changes

Evidence:
  - All DB queries execute in < 1 ms on local dataset
  - All relations prefetched (no N+1)
  - workspace_id index exists — will be used by planner at production-scale row counts
  - issues_workitems_idx partial index covers the (parent_id IS NULL, deleted_at IS NULL,
    archived_at IS NULL, is_draft = false) predicate pattern used in HO views
  - Adding a composite index would be speculative (YAGNI) — not justified by EXPLAIN evidence

## High TTFB root cause (per debug report: 400-407 ms)
  NOT DB latency. Caused by multiple concurrent HTTP requests from:
    - ho-datasheet-view.tsx useEffect firing fetchFilterOptions()
    - ho-category-view.tsx useEffect firing fetchFilterOptions()
    - No in-flight dedupe in store
  Fix: Track A (frontend) — single mount effect in ho/page.tsx + _filterOptionsInflight guard in store.
