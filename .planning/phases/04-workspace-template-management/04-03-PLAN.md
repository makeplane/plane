<objective>
Deliver the create/edit vertical slice: a full-page structured template editor (D-09) that saves the whole template atomically (D-10) through new `ProjectService` methods, with the two order-sensitive sections — States and Labels — fully working including drag reorder (D-11), hidden auto-generated stable reference keys (D-12), and inline backend-error surfacing. After this plan an admin can create and edit a custom template end-to-end with states and labels. Modules/Cycles/Starter-issues sections and their cross-references are added in Plan 04; lifecycle actions in Plan 05.

Purpose: This is the core authoring path for UI-05 and establishes the RHF + `useFieldArray` form model, the payload-assembly/key-generation utilities, and the five service methods the rest of the phase depends on.
Output: five service methods + `include_inactive` param, `TProjectTemplateWritePayload` type, editor pages/headers (new + edit), the RHF editor root, States + Labels sections, and `utils.ts`.

Scope note (intentional density): this plan touches ~13 files across two tasks, but the density is deliberate and within budget. Task 1 is a self-contained foundation slice (service methods + write-payload type + fetch keys + utils, no UI). Task 2's four page/header files (`new/page`, `new/header`, `[templateId]/edit/page`, `[templateId]/edit/header`) are thin shells — admin gate + `SettingsContentWrapper` + breadcrumb + mounting `ProjectTemplateEditorRoot` — with the real logic concentrated in `root.tsx` + the two section components. Splitting foundation from UI would force renumbering Plans 04/05 and rewiring their `depends_on`/threat IDs for no execution-risk reduction, since the two tasks are already cleanly separated (foundation → UI) and the page files carry negligible logic. Kept as one plan by design.
</objective>
