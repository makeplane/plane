# مرحله ۱: زمان‌سنجی (Time Tracking)

وضعیت: پیاده‌سازی و تست شده روی سیستم توسعه. **هنوز روی سرور اعمال نشده**.
برنچ: `feat/team-ops-time-tracking` (commit نشده).

## قابلیت‌ها

- تایمر زنده: شروع و توقف، با اتصال اختیاری به یک Work Item و یادداشت. هر کاربر در هر ورک‌اسپیس حداکثر یک تایمر فعال دارد.
- ثبت دستی زمان: تاریخ، ساعت شروع، مدت (ساعت و دقیقه)، یادداشت، قابل‌صورت‌حساب بودن.
- ویرایش و حذف ورودی‌ها.
- نمای هفتگی: جمع کل، جمع قابل‌صورت‌حساب، نمودار روزانه، لیست ورودی‌ها، رفتن به هفته‌ی قبل/بعد. شروع هفته از تنظیم پروفایل کاربر می‌آید.
- صفحه در `/<workspace>/team-ops/time` و آیتم «Time tracking» زیر آیتم‌های سنجاق‌شده‌ی سایدبار.

## قواعد مهم

| قاعده            | جزئیات                                                                                                         |
| ---------------- | -------------------------------------------------------------------------------------------------------------- |
| دسترسی           | Guest ممنوع. Member فقط ورودی‌های خودش. Admin همه را می‌بیند، ویرایش و حذف می‌کند (ثبت ورودی فقط برای خود).    |
| Work Item        | فقط Work Item همین ورک‌اسپیس و در پروژه‌ای که کاربر عضو فعالش است. پاسخ «پیدا نشد» و «دسترسی نداری» یکسان است. |
| حداکثر مدت       | هر ورودی حداکثر ۲۴ ساعت (قید دیتابیس هم دارد).                                                                 |
| زمان آینده       | بیش از ۵ دقیقه جلوتر از ساعت سرور رد می‌شود.                                                                   |
| تایمر فراموش‌شده | هنگام توقف بیش از ۲۴ ساعت، فقط ۲۴ ساعت ثبت می‌شود و پاسخ `capped: true` دارد؛ UI هشدار می‌دهد.                 |
| حذف              | حذف نرم (`deleted_at`) برای ورودی‌ها؛ تایمر هنگام توقف حذف سخت می‌شود.                                         |
| خاموش کردن       | متغیر محیطی `TEAM_OPS_ENABLED=0` مسیرهای API را برمی‌دارد (پیش‌فرض روشن). جدول‌ها همیشه ساخته می‌شوند.         |

### نتیجه‌ی تست روی بکاپ واقعی سرور

بکاپ `plane-db.dump` (۲۰۲۶-۱۰-۳۰) در یک Postgres 16 جدا restore شد (۲۲ کاربر، ۵ ورک‌اسپیس، ۱۰ پروژه، ۴۷۹ Work Item) و `manage.py migrate` اجرا شد:

- مایگریشن‌های `db.0122` تا `db.0125` و `team_ops.0001` بدون خطا اجرا شدند.
- شمار ردیف همه‌ی ۱۱۰ جدول قبلی **قبل و بعد یکسان** ماند، به‌جز جدول‌های متادیتای Django (`django_migrations`, `django_content_type`, `auth_permission`).
- دو جدول جدید اضافه شد؛ هیچ جدولی حذف نشد.

**نکته‌هایی که از مایگریشن‌های آپ‌استریم (`0122–0125`) باید بدانید:**

- `0123` دو ستون `is_service` و `allowed_rate_limit` را از `api_tokens` حذف می‌کند. روی سرور شما ۱ توکن API با `allowed_rate_limit` غیرخالی هست؛ آن مقدار از بین می‌رود (بکاپ دارد). `is_service` همه `false` بود.
- `0125` فقط روی `deploy_boards` پروژه‌ها کار می‌کند؛ روی سرور شما هیچ board منتشرشده‌ای نیست، پس اثری ندارد.

## API (همه زیر `/api/workspaces/<slug>/team-ops/`)

| متد و مسیر                            | کار                                                                                                                                          |
| ------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------- |
| `GET time-entries/`                   | فهرست صفحه‌بندی‌شده؛ فیلتر `user` (فقط Admin برای دیگران)، `issue`, `project`, `from`, `to` (تاریخ یا datetime). مرتب نزولی بر `started_at`. |
| `POST time-entries/`                  | ثبت دستی: `started_at` به‌علاوه `ended_at` یا `duration_seconds`، اختیاری `issue`, `note`, `is_billable`.                                    |
| `GET/PATCH/DELETE time-entries/<id>/` | خواندن، ویرایش، حذف.                                                                                                                         |
| `GET time-entries/summary/?from=&to=` | جمع کل و قابل‌صورت‌حساب، تفکیک روز و ۱۰ Work Item برتر. بازه الزامی و حداکثر ۳۶۶ روز.                                                        |
| `GET timer/`                          | `{"timer": {...} \| null}`                                                                                                                   |
| `POST timer/`                         | شروع (`issue`, `note` اختیاری). اگر تایمر فعال باشد `409` به‌همراه تایمر فعلی.                                                               |
| `DELETE timer/`                       | توقف و ساخت ورودی؛ `201 {"entry": {...}, "capped": bool}`، بدون تایمر `404`.                                                                 |

## محدودیت‌ها و کارهای باقی‌مانده

1. **UI در مرورگر اجرا نشده.** نبود Docker/Redis روی این سیستم باعث شد کل استک بالا نیاید. قبل از استقرار یک بار صفحه را روی استک محلی دستی امتحان کنید (شروع/توقف تایمر، ثبت دستی، ویرایش، حذف، جابه‌جایی هفته).
2. **مرز روز و منطقه‌ی زمانی:** هفته در منطقه‌ی مرورگر محاسبه می‌شود ولی تفکیک روزانه‌ی API بر منطقه‌ی زمانی پروفایل کاربر است. اگر این دو فرق داشته باشند، ورودی‌های نزدیک نیمه‌شب می‌توانند در روز مجاور بنشینند.
3. **دکمه‌ی تایمر در صفحه‌ی خود Work Item** هنوز اضافه نشده (برای حداقل‌ماندن تغییر در Core). فعلاً Work Item از داخل صفحه‌ی زمان‌سنجی انتخاب می‌شود.
4. **فلگ فرانت:** با `TEAM_OPS_ENABLED=0` آیتم سایدبار هنوز نمایش داده می‌شود ولی API پاسخ ۴۰۴ می‌دهد.
5. **ترجمه‌ها ماشینی‌اند** و باید بازبینی بومی شوند (طبق راهنمای `translate`). زبان فارسی در پلین وجود ندارد؛ افزودن آن یک کار مستقل بزرگ است (همه‌ی ~۳۹۰۰ کلید + RTL).
6. **جمع‌های هفتگی برای Admin:** صفحه فقط ورودی‌های خود کاربر را نشان می‌دهد. نمای تیمی در ماژول «داشبورد مدیریت» می‌آید.
7. **تغییرات معماری نسبت به `ARCHITECTURE.md`:** تست‌ها زیر `plane/tests/` (چون fixtureها آنجاست)، سرویس فرانت در `packages/services`، و به‌جای store از نوع MobX از SWR استفاده شد تا root store Core دست نخورد.
