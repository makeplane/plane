## 0. 文档定位

本文用于回答以下问题：

1. PiLab 是否应建设微信小程序，以及小程序在现有 Web 产品中的定位。
2. 首个可上线版本应包含哪些业务能力，哪些能力继续留在 Web。
3. 小程序如何复用现有 Django API、科研权限、审计和工作流，同时解决微信身份、Token、附件和消息等平台差异。
4. 产品、设计、前端、后端、测试、运维分别需要交付什么，以及如何验收。

本文是小程序的产品与技术执行基线，不代表所有功能已经进入开发。未被本文明确纳入 MVP 的能力，不得以“与 Web 保持一致”为由自动加入首期排期。

阅读建议：

- 产品与业务方：§1–§6、§13、§16。
- 交互与视觉设计：§4–§7。
- 小程序前端：§7–§11。
- 后端与安全：§8–§12。
- 测试、运维与发布：§13–§17。

## 1. 背景与问题

PiLab 已在 Web 端提供工作空间、项目、工作项、科研报告、阶段流程、多人评审、实验记录、成果登记和办公审批等能力。科研和行政人员的高频操作大量发生在离开电脑的场景，例如：

- 查看和处理分配给自己的任务。
- 接收报告提交、退回、评审和审批提醒。
- 快速填写当日实验记录或周报草稿。
- 导师和主 PI 在会议、出差或实验现场完成评审与审批。
- 通过群聊分享的链接快速打开指定任务、报告或审批单。

当前仅提供 Web 入口，存在以下问题：

1. 手机浏览器入口深、登录链路长，高频轻操作成本较高。
2. 浏览器通知在微信生态中的到达率和使用习惯不稳定。
3. 桌面信息架构在窄屏上密度过高，复杂表格、拖拽和富文本编辑不适合直接缩放。
4. 现有 Web 使用浏览器 Cookie、CSRF、DOM 富文本和实时协作技术，不能直接编译为微信小程序。

现有路线图已把响应式 Mobile Web 纳入 P2。小程序不是 Mobile Web 的替代品：Mobile Web 负责复杂页面的移动可访问性，小程序负责高频、短链路和微信触达。

## 2. 产品决策

### 2.1 核心定位

> PiLab 微信小程序是与 Web 共用同一业务后端的移动工作台，不是桌面端的完整复制品。

小程序聚焦“查看、处理、快速记录、消息触达”四类任务；复杂配置、批量操作、协同富文本、专业看板和大文件处理继续由 Web 承担。

### 2.2 建设原则

1. **单一数据源**：Web 与小程序读写同一套 Django API 和数据库，不建立独立业务库，不做客户端之间的数据同步。
2. **权限同源**：小程序不另建科研权限规则，所有结果由服务端现有 ACL、角色和状态机裁决。
3. **审计同源**：小程序写操作进入现有审计链，并额外记录客户端类型和版本。
4. **移动优先取舍**：为手机场景重新设计信息层级，不追求页面一比一复刻。
5. **渐进交付**：先做技术验证和 MVP，再依据真实使用数据决定扩展范围。
6. **Web 可兜底**：不适合小程序承载的操作提供明确的 Web/H5 入口，而不是做能力残缺的仿制页面。

### 2.3 方案选择

| 方案                      | 优点                                   | 局限                                 | 结论                                   |
| ------------------------- | -------------------------------------- | ------------------------------------ | -------------------------------------- |
| 仅响应式 Mobile Web       | 成本最低、复用率最高、无需微信审核     | 微信触达弱，入口和登录体验一般       | 必须建设，作为移动基础与复杂功能兜底   |
| 小程序 `web-view` 套壳    | 验证快、短期代码少                     | 登录、导航、分享、附件和审核体验受限 | 仅允许用于内部技术验证，不作为正式架构 |
| 原生微信小程序            | 平台能力完整、体验可控                 | 与 React Web 复用率低，维护两套 UI   | 不选，团队维护成本过高                 |
| Taro + React + TypeScript | 延续 React/TS 能力，可复用类型和纯逻辑 | Web DOM 组件仍需重写                 | **推荐正式方案**                       |
| uni-app                   | 生态成熟、跨端能力较强                 | 与现有 React 技术栈和人才结构不一致  | 不选                                   |

## 3. 目标、非目标与成功指标

### 3.1 MVP 目标

| 编号 | 目标               | 可验证结果                                           |
| ---- | ------------------ | ---------------------------------------------------- |
| G1   | 降低移动访问成本   | 已绑定用户可在小程序启动后快速进入“我的工作台”       |
| G2   | 覆盖核心待办闭环   | 用户可查看并完成任务、报告、审批和评审的首期操作     |
| G3   | 支持现场快速记录   | 用户可创建实验记录、保存报告草稿并上传图片或小型文档 |
| G4   | 建立可靠身份链     | 微信身份只能绑定既有 PiLab 身份，权限与 Web 完全一致 |
| G5   | 建立可运营发布体系 | 可观测客户端版本、接口错误、消息触达和关键漏斗       |
| G6   | 不破坏既有系统     | Web、API、科研状态机和权限规则保持向下兼容           |

### 3.2 MVP 非目标

以下能力不进入首期：

- 组织树、工作空间、模板、身份映射和平台配置。
- 用户批量导入、邀请码管理和审计后台。
- 甘特图、复杂数据表、高级看板、拖拽排序和批量编辑。
- 完整 Page 编辑、Tiptap/ProseMirror/Yjs 实时协作。
- 代码仓库快照上传、大文件归档和集成连接配置。
- 在小程序内完成 AI4MS 生态中其他专业系统的复杂操作。
- 离线写入与离线冲突合并。
- 与 Web 所有页面和操作一比一对等。

### 3.3 上线后指标

试点期以四周为一个观察窗口：

| 指标                      | MVP 目标                |
| ------------------------- | ----------------------- |
| 绑定成功率                | ≥ 95%，排除用户主动取消 |
| 登录成功率                | ≥ 99%                   |
| 首页核心数据加载成功率    | ≥ 99%                   |
| 关键写操作成功率          | ≥ 99%                   |
| 小程序崩溃率              | < 0.2%                  |
| P95 首页可交互时间        | Wi-Fi/5G 下 ≤ 2.5 秒    |
| 待办详情打开 P95          | ≤ 2 秒                  |
| 试点用户周活跃率          | ≥ 40%                   |
| 移动端完成的审批/评审占比 | ≥ 30%                   |
| 严重越权事件              | 0                       |

指标是试点目标，不作为绕过安全、审计或状态机校验的理由。

## 4. 用户与核心场景

### 4.1 用户角色

小程序不新增业务角色，沿用 PiLab 现有身份：

| 用户                            | 主要诉求                                                 |
| ------------------------------- | -------------------------------------------------------- |
| Research Owner                  | 查看任务，填写报告和实验记录，提交阶段材料，跟踪退回意见 |
| 直接导师                        | 查看被指导成员进展，处理报告与阶段评审，给出意见         |
| 课题组主 PI                     | 查看本组重点待办，处理评审和审批，发现阻塞               |
| Reviewer                        | 查看待我评审，提交结论和评分                             |
| Workspace Admin / InstanceAdmin | 仅处理适合移动端的待办；复杂管理继续进入 Web             |
| 普通成员                        | 查看和处理被授权的工作项与通知                           |

### 4.2 关键用户旅程

#### 旅程 A：首次绑定

```text
打开小程序
  → 微信授权登录
  → 服务端识别为未绑定
  → 选择“绑定已有 PiLab 账号”
  → 在 AI4MS/PiLab 完成身份认证或输入一次性绑定码
  → 服务端校验账号状态并建立绑定
  → 展示绑定结果与可进入的工作空间
```

不得通过微信昵称、头像、手机号或邮箱猜测并自动合并账号。

#### 旅程 B：移动审批

```text
收到订阅消息或进入“待办”
  → 打开审批详情
  → 查看申请信息、附件、流程和历史
  → 同意或拒绝；拒绝必须填写原因
  → 二次确认
  → 服务端执行现有审批状态机并写审计
  → 小程序刷新结果，站内通知相关人员
```

#### 旅程 C：填写周报

```text
进入“报告”
  → 打开本周期周报
  → 编辑简化 Markdown/纯文本正文
  → 保存草稿并上传图片/文档
  → 查看可见范围与提交检查
  → 提交
  → 服务端生成正式版本并通知导师/主 PI
```

#### 旅程 D：现场记录实验

```text
进入科研项目
  → 新建实验记录
  → 填写标题、目的、方法、结果和状态
  → 拍照或从会话/相册选择图片
  → 保存草稿或提交
  → 提交后按现有规则锁定关键字段
```

## 5. 功能范围与优先级

### 5.1 MVP（P0，必须上线）

| 模块     | 功能                                          | 说明                               |
| -------- | --------------------------------------------- | ---------------------------------- |
| 身份     | 微信登录、账号绑定、解绑、设备会话            | 支持主动退出和管理员吊销           |
| 工作台   | 我的任务、待审批、待评审、报告状态、快捷入口  | 使用移动聚合 API 一次返回          |
| 工作空间 | 列表、切换、最近使用                          | 只显示服务端授权空间               |
| 工作项   | 列表、搜索、筛选、详情、状态、负责人、评论    | 不含拖拽、复杂视图配置和批量操作   |
| 科研总览 | 我的科研项目、阶段状态、近期阻塞              | 按身份裁剪                         |
| 报告     | 周报/月报列表、草稿编辑、提交、历史、退回意见 | 简化编辑器，不做实时协同           |
| 审批     | 待我处理、详情、同意、拒绝、历史              | 复用现有审批状态机                 |
| 评审     | 待我评审、材料只读、评分、结论、意见          | 禁止评审本人提交内容               |
| 实验     | 列表、详情、新建、草稿、提交、图片附件        | 修订审批仅查看，首期不在小程序发起 |
| 阶段     | 阶段时间线、材料状态、gate 结果、评审结果     | 复杂材料编辑转 Web                 |
| 通知     | 站内通知列表、已读、订阅消息跳转              | 站内通知是事实来源                 |
| 分享     | 分享任务、报告、审批、评审和实验详情          | 接收者仍需通过服务端权限校验       |
| 我的     | 个人资料只读、绑定状态、版本、隐私说明、退出  | 资料编辑转 Web                     |

### 5.2 增强版（P1，MVP 数据验证后排期）

- 审批流发起和更多审批类型。
- 阶段材料简化编辑与提交。
- 实验修订申请和处理。
- 文献登记、DOI 查询和状态维护。
- 成果登记和外部引用查看。
- 课题组移动风险看板。
- 小程序码进入指定项目或公共活动页。
- 消息订阅偏好和提醒频率配置。

### 5.3 Web/H5 兜底范围

遇到下列操作时，小程序显示原因和“在网页版继续”按钮：

- 复杂富文本、协同 Page、版本对比。
- 组织、权限、模板、集成和平台设置。
- 批量导入、导出和批量编辑。
- 甘特图、复杂看板、大型表格。
- 大于小程序策略上限的文件和代码快照。

若微信环境限制直接打开外部页面，应复制链接或通过已备案业务域名的 `web-view` 打开；不得静默失败。

## 6. 信息架构与页面需求

### 6.1 底部导航

MVP 使用四个 Tab：

1. **工作台**：聚合核心待办和快捷入口。
2. **任务**：工作项列表、搜索、筛选和详情。
3. **科研**：科研项目、报告、阶段、实验和评审。
4. **我的**：工作空间、身份绑定、通知设置和版本信息。

审批和评审通过工作台卡片及科研页二级入口进入，不单独占用 Tab。

### 6.2 工作台

必须展示：

- 当前工作空间及切换入口。
- 待我处理：任务、审批、评审、报告退回四类数量。
- 最近任务和即将到期任务。
- 当前周期报告状态。
- 我的科研项目阶段状态与阻塞摘要。
- 通知未读数。

空状态必须区分“暂无数据”“没有权限”“模块未启用”和“网络失败”。

### 6.3 任务列表与详情

列表支持：分配给我、我创建的、即将到期、已逾期，以及状态/项目/优先级筛选。默认分页或游标加载，不一次拉取全量数据。

详情支持：

- 标题、描述只读渲染、状态、负责人、优先级、日期、标签。
- 评论列表和新增纯文本评论。
- 小型附件预览与下载。
- 允许时修改状态、负责人和截止日期。
- 查看活动历史。

不支持复杂属性布局、子任务拖拽、关系图和工作项视图配置。

### 6.4 报告

报告编辑采用受控的简化 Markdown/纯文本输入，支持标题、段落、列表、引用和链接。服务端保存格式必须与现有报告正文兼容，不引入仅小程序能解析的新格式。

提交前展示：

- 周期、报告类型和当前状态。
- 可见范围及其解释。
- 附件清单。
- gate/必填项检查结果。
- “提交后生成正式版本”的明确提示。

### 6.5 审批与评审

所有不可逆操作均需二次确认。拒绝、退回和需修改必须填写原因；通过可按既有流程决定是否要求意见。

材料正文首期只读展示。无法安全渲染的节点降级为纯文本或附件下载，不执行任意 HTML、脚本或外链资源。

### 6.6 实验记录

创建表单按移动场景拆为“基本信息—过程—结果—附件”四段，允许分段保存草稿。字段、状态和提交后锁定规则与 Web 一致。

SMILES、结构化 parameters/metrics 等复杂字段首期只读或以键值对简化录入，不在小程序实现专业编辑器。

## 7. 交互、视觉与可用性要求

1. 设计宽度覆盖主流手机，不以平板或横屏为首要目标。
2. 触控目标不得过小；关键操作置于拇指可达区域。
3. 表格在移动端转换为卡片、分组列表或详情页，不使用横向缩放复刻桌面表格。
4. 所有网络写操作提供提交中、成功、失败和可重试状态，防止重复提交。
5. 状态、风险和审批结论不能只依赖颜色表达。
6. 危险操作使用明确动词，不使用含糊的“确定”。
7. 长表单支持草稿、离开提醒和重新进入恢复；MVP 不承诺离线提交。
8. 中英文文案进入现有 i18n 体系；MVP 默认简体中文，保留英文扩展能力。
9. 无障碍至少覆盖文本缩放、读屏标签、焦点顺序和颜色对比度。

## 8. 总体技术架构

### 8.1 架构图

```text
┌──────────────────┐       ┌──────────────────┐
│ React Web / H5   │       │ 微信小程序 Taro  │
│ Cookie + CSRF    │       │ Bearer Token     │
└────────┬─────────┘       └────────┬─────────┘
         │                          │
         │ existing API            │ /api/mobile/v1 + existing API
         └─────────────┬────────────┘
                       ▼
             ┌─────────────────────┐
             │ Django API          │
             │ 共享服务/ACL/审计   │
             └───────┬─────────────┘
                     │
          ┌──────────┼───────────┐
          ▼          ▼           ▼
      PostgreSQL   Redis      对象存储
```

移动聚合 API 在 Django 进程内调用共享 service/query 层，不通过 HTTP 再请求既有 API，不复制权限逻辑。

### 8.2 仓库结构建议

```text
apps/
  mini-program/             # Taro + React + TypeScript
    src/
      api/                  # wx.request 适配、Token 刷新、错误归一化
      pages/
      components/
      stores/
      features/
      telemetry/
packages/
  types/                    # 复用无浏览器依赖的接口类型
  constants/                # 复用端点/枚举，按运行时边界拆分导出
apps/api/plane/mobile/      # 移动认证、聚合接口、客户端版本策略
```

不得从小程序导入 `@plane/ui`、`@plane/editor` 或依赖 DOM、`window`、`document`、IndexedDB 的模块。共享代码以纯 TypeScript 类型、枚举、校验和无副作用函数为限。

### 8.3 前端选型

- Taro、React、TypeScript 严格模式。
- 状态管理优先选择轻量且适合小程序运行时的方案；不为了表面复用强行搬入完整 Web MobX Store。
- 网络层基于 `Taro.request`/`wx.request` 封装，不使用当前依赖 Cookie 的 Axios 实例。
- 缓存使用小程序 Storage，并设置用户、工作空间、资源和版本维度；退出或解绑时彻底清理。
- 包体积从设计阶段控制，按页面分包，专业模块延迟加载。

## 9. 身份、会话与账号绑定

### 9.1 身份模型

新增微信身份绑定，建议数据模型：

| 字段                    | 说明                                             |
| ----------------------- | ------------------------------------------------ |
| `user_id`               | PiLab 用户，唯一业务主体                         |
| `app_id`                | 微信小程序 AppID                                 |
| `open_id`               | 当前小程序内稳定标识，与 `app_id` 组合唯一       |
| `union_id`              | 在满足微信条件时保存，可空；不得单独作为授权依据 |
| `bound_at` / `bound_by` | 绑定时间与方式                                   |
| `last_login_at`         | 最近登录时间                                     |
| `status`                | `ACTIVE / REVOKED`                               |

设备会话单独建模，保存 refresh token 摘要、设备标识摘要、有效期、最近使用时间、撤销时间和客户端版本。数据库不得保存明文 refresh token。

### 9.2 登录流程

1. 小程序调用 `wx.login` 获取一次性 code。
2. 小程序将 code 发送至后端 `/api/mobile/v1/auth/wechat/login`。
3. 后端通过微信服务端接口换取身份信息；AppSecret 只存在服务端密钥系统。
4. 已绑定用户获得短期 access token 和轮换式 refresh token。
5. 未绑定用户获得短期 `binding_ticket`，只能进入绑定流程，不能访问业务 API。
6. 绑定通过 AI4MS/PiLab 登录后的单次授权码，或由已登录 Web 生成的一次性绑定码完成。
7. 后端建立微信身份映射、写审计并签发业务 Token。

禁止在小程序中保存 AI4MS/OIDC 密码，也不得把现有浏览器 Session Cookie 转换为长期客户端凭据。

### 9.3 Token 策略

- Access token 建议 15–30 分钟有效，只放在 `Authorization: Bearer`。
- Refresh token 建议 30 天以内，可按安全策略缩短；每次刷新后轮换旧 Token。
- 支持单设备退出、全部设备退出、管理员吊销和密码/身份风险事件后的全量吊销。
- Token 绑定 `client_id=wechat-mini-program`、用户、会话和权限版本。
- 刷新失败时清理本地会话并引导重新登录，不做无限重试。
- 写接口保留幂等键或客户端请求 ID，防止弱网重试造成重复审批或重复提交。

### 9.4 绑定安全规则

- 微信身份不能自动扩大工作空间成员关系或科研 ACL。
- 一个微信身份同一时间只能绑定一个有效 PiLab 用户。
- 一个 PiLab 用户是否允许绑定多个微信身份由实例策略控制，默认允许一个。
- 解绑前二次确认；解绑、重绑、失败冲突和管理员撤销均写审计。
- 账号禁用、删除或失去工作空间席位后，小程序权限立即按服务端结果收敛。

## 10. API 与数据契约

### 10.1 移动 API

新增版本化命名空间 `/api/mobile/v1/`：

| 接口                               | 用途                                   |
| ---------------------------------- | -------------------------------------- |
| `POST /auth/wechat/login`          | 微信 code 登录或获取绑定票据           |
| `POST /auth/bind`                  | 消费一次性绑定授权                     |
| `POST /auth/refresh`               | 轮换 Token                             |
| `POST /auth/logout`                | 注销当前设备会话                       |
| `GET /auth/sessions`               | 查看设备会话                           |
| `DELETE /auth/sessions/<id>`       | 吊销指定设备                           |
| `GET /bootstrap`                   | 当前用户、工作空间、功能开关、版本策略 |
| `GET /workspaces/<slug>/dashboard` | 工作台聚合数据                         |
| `GET /workspaces/<slug>/todo`      | 统一待办列表                           |
| `POST /subscriptions`              | 保存订阅消息授权结果和场景             |
| `GET /client-policy`               | 最低兼容版本、升级提示和维护信息       |

任务、报告、审批、评审、实验等细节接口优先复用现有 `/api/` 与 `/api/research/`。只有出现明显多请求瀑布、响应体过大或移动字段需求时才增加聚合/投影接口。

### 10.2 通用请求头

小程序请求至少携带：

- `Authorization: Bearer <access_token>`
- `X-Client-Platform: wechat-mini-program`
- `X-Client-Version: 3.1.0`
- `X-Client-Build: <微信构建号>`
- `X-Request-ID: <UUID>`
- 写操作按需携带 `Idempotency-Key`

服务端日志与审计不得记录完整 Token、微信 code、绑定票据或敏感正文。

### 10.3 分页、错误和兼容

- 新列表接口统一游标或明确的 `page/page_size` 契约，禁止隐式返回全量。
- 错误响应至少包含稳定 `error_code`、用户可读消息、`request_id` 和可否重试标记。
- 权限不足与对象不存在继续遵循既有防枚举策略，不因小程序增加对象存在性泄露。
- `/api/mobile/v1` 内只做向下兼容扩展；破坏性变更进入 `/v2`。
- 服务端至少兼容当前已发布和前一个仍在微信审核/灰度中的小程序版本。

### 10.4 数据一致性

- Web、小程序和外部集成写入同一数据库，不存在客户端同步任务。
- 状态变更成功后以服务端响应为准，客户端乐观更新失败必须回滚。
- 多端同时编辑报告草稿时使用 `updated_at`/版本号进行冲突检测；MVP 提示刷新或覆盖，不做自动合并。
- 审批、评审、报告提交、阶段流转等动作必须在服务端事务中完成。

## 11. 内容、附件和外链

### 11.1 富文本策略

现有 Web 编辑器依赖 Tiptap、ProseMirror、Yjs 和 DOM，不能进入小程序包。MVP 采用以下策略：

- 只读：服务端提供经过白名单清洗的移动内容投影，优先渲染结构化 JSON 或受控 Markdown。
- 编辑：报告和评论使用简化 Markdown/纯文本；复杂 Page 和阶段材料转 Web。
- 未支持节点：显示占位说明，不丢弃源内容，不在客户端执行 HTML。
- 图片：通过受控资源接口获取，校验 ACL 后签发短时 URL。

### 11.2 附件策略

- MVP 支持相机/相册图片以及常见的小型 PDF、Office 文档。
- 产品建议上限：单图 20 MB、单文档 20 MB；最终由实例配置和微信平台能力共同取较小值。
- 100 MB 报告 PDF、500 MB 代码快照等大文件只允许 Web 处理。
- 上传复用对象存储预签名机制；若微信运行时无法稳定执行现有 POST 策略，则增加受认证的小文件上传代理，不改变最终 FileAsset 权威模型。
- 下载前始终重新校验资源 ACL；分享链接不携带永久签名 URL。
- 微信 `request/uploadFile/downloadFile`、对象存储和业务 Web 域名均需 HTTPS、备案并加入合法域名配置。

### 11.3 外链与分享

- 分享参数只包含短期 scene/token 或资源类型和不敏感标识，不包含姓名、报告标题、Token 或签名下载地址。
- 接收者打开后必须登录并重新进行工作空间、资源和动作级权限校验。
- 外部系统链接使用域名白名单；不支持的小程序外链给出复制链接或 Web 继续方式。

## 12. 通知与微信订阅消息

### 12.1 消息原则

站内通知是业务事实来源，微信订阅消息只是尽力而为的提醒通道。用户拒绝订阅、模板失效、发送失败或微信限流不得影响审批、评审和报告流程。

### 12.2 MVP 消息场景

- 新任务分配和临近截止。
- 报告提交成功、被退回或被验收。
- 新审批待办与审批结果。
- 新阶段评审待办与评审结果。

同一业务事件必须去重，避免站内、邮件和微信重复轰炸。订阅授权按微信规则在合适业务场景请求，不在启动页无目的索取。

### 12.3 跳转

每条订阅消息携带受控页面路径和资源标识。进入小程序后先恢复登录和工作空间上下文，再查询资源；无权限、已删除或流程已结束时展示明确状态，而不是空白页。

## 13. 安全、隐私与合规

上线前必须完成：

1. 小程序主体、类目、备案、业务域名和服务器域名确认。
2. 用户隐私保护指引、第三方 SDK 清单、收集字段和用途说明。
3. 微信 OpenID/UnionID、手机号、头像等个人信息的最小化收集评审。
4. Token、AppSecret、对象存储密钥全部置于服务端密钥管理，不进入代码仓库和小程序包。
5. 移动认证、账号绑定、分享 scene、附件下载和聚合 API 的越权测试。
6. 日志脱敏、审计留存、账号注销和身份解绑流程。
7. Taro、微信 SDK 和第三方依赖的供应链扫描。
8. AGPL-3.0 许可义务复核，明确小程序客户端及服务端修改的源码提供方式。

高风险动作沿用服务端权限检查，客户端隐藏按钮不能作为安全边界。服务端对登录、绑定、刷新、验证码/一次性码和写接口实施分层限流。

## 14. 非功能要求与可观测性

### 14.1 性能与稳定性

- 首屏只请求 bootstrap 和工作台聚合数据，避免多接口瀑布。
- 列表分页，图片缩略图化，详情按需加载。
- 弱网下显示缓存数据及更新时间；写操作不允许假成功。
- API 超时、重试和熔断按读写区分：幂等 GET 可有限重试，非幂等写操作依赖请求 ID/幂等键。
- 小程序维护窗口和最低兼容版本由远端策略控制。

### 14.2 埋点与日志

最少采集以下不含正文的事件：

- 启动、登录、绑定开始/成功/失败、退出。
- 工作空间切换、首页加载结果。
- 任务/报告/审批/评审/实验页面打开与动作结果。
- 订阅消息授权、发送结果和落地页打开。
- Web 兜底跳转。
- API 错误码、耗时、请求 ID、客户端版本和网络类型。

禁止把报告正文、评论、实验结果、附件名称、Token 和微信 code 作为埋点属性。

### 14.3 告警

建立以下告警：登录失败率、绑定冲突率、Token 刷新失败率、核心接口 5xx、关键写操作失败率、订阅消息失败率和客户端版本异常分布。所有告警应能通过 `request_id` 关联服务端日志。

## 15. 版本、发布与兼容策略

### 15.1 三层版本

| 版本              | 用途                            | 示例                        |
| ----------------- | ------------------------------- | --------------------------- |
| PiLab 产品版本    | Web、API 和共享包的语义化版本   | `3.1.0`                     |
| 小程序产品版本    | 表示与 PiLab 产品能力的对应关系 | `3.1.0`                     |
| 微信构建/审核版本 | 同一产品版本的修订和审核批次    | `mp.1`、`mp.2` 或平台构建号 |

本 PRD 作为文档和规划变更随 `3.0.4` 提交；真正交付小程序 MVP 属于向下兼容的新功能，建议升次版本到 `3.1.0`。

### 15.2 兼容规则

- 小程序不得要求与服务端精确同版本，只声明支持的 API 主版本和最低服务端能力。
- `/bootstrap` 返回 `minimum_client_version`、`recommended_client_version` 和 feature flags。
- 普通升级只提示；仅安全问题或无法兼容的协议变更才阻止继续使用。
- 微信审核期间不得提前删除旧字段或旧接口。
- 灰度回滚以关闭 feature flag、回退服务端兼容实现和撤回小程序版本为主，不依赖数据库回滚。

### 15.3 发布流程

```text
本地与自动化测试
  → 微信开发版联调
  → 内部体验版验收
  → 安全/隐私/许可证检查
  → 微信审核
  → 小范围灰度
  → 指标与告警观察
  → 全量发布
```

## 18. 风险与应对

| 风险                             | 等级 | 应对                                                 |
| -------------------------------- | ---- | ---------------------------------------------------- |
| 微信身份与现有 OIDC 身份错误合并 | 高   | 只允许一次性授权绑定，不以个人资料猜测身份           |

## 20. 最终建议

1. 批准“小程序移动工作台”定位，不批准“完整复制 Web”定位。
2. 先完成 2 周 M0 技术 Spike；通过退出条件后再锁定 10–14 周 MVP 排期。
3. 小程序与 Mobile Web 并行规划：小程序承担高频处理和消息触达，Mobile Web 承担复杂能力兜底。
4. 后端优先投入移动认证、聚合 API、内容投影和客户端兼容策略，这些是成败关键。
5. MVP 对应 PiLab `3.1.0`，微信审核构建号独立递增；不得因审核节奏强制 Web 与小程序同步上线。
